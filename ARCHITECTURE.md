# Bridge architecture

## Where Bridge sits

```
 User
  |
  v
 Planning assistant        (future integration; not present in this milestone)
  |                        implements src/providers/adapter.ts
  v
 Bridge                    (this VS Code extension)
  |     extension host: config, controller, OpenCode client
  |     webview: chat UI, no credentials, no network
  v
 OpenCode server           (localhost, HTTP Basic auth, /api/*)
```

The planning-assistant layer is a documented seam, not a feature. `adapter.ts` defines
what a future assistant must implement, and one rule is already enforced in code:
**approval requests are never auto-answered** - they always go to the user, no matter
which assistant is registered. There is no ChatGPT/Claude login, scraping or auth
bypass anywhere in Bridge, and none should be added inside this extension: a real
integration must be an authorized API and lives behind the adapter interface.

## Modules

| Module | Responsibility |
| --- | --- |
| `src/config.ts` | Pure functions: state-file discovery (`~/.local/state/opencode/service.json`), endpoint resolution, loopback enforcement, Basic auth header, secret redaction. No VS Code types, fully unit-tested. |
| `src/opencode/connection.ts` | Owns the one SDK client and the connection state machine (disconnected / connecting / connected / error). Classifies failures into human explanations (nothing listening, auth rejected, timeout, unexpected response), deduplicates overlapping connect attempts, and supplies the secrets that must be redacted from anything user-visible. |
| `src/opencode/stream.ts` | Subscribes to OpenCode's SSE event stream, normalises `V2Event` into flat `BridgeStreamEvent`s, reconnects with backoff, and remembers tool names (they only arrive on `session.tool.input.started`). |
| `src/opencode/sessions.ts` | `SessionGateway`: workspace description, session list/create, prompt enqueue, interrupt, history loading, default model lookup. Converts stored OpenCode messages into chat entries. |
| `src/controller.ts` | Owns the chat state the UI shows: session selection, the duplicate-submission gate, streaming updates, cancellation, and the authoritative resync from stored messages after every turn. |
| `src/webview/protocol.ts` | The host <-> webview contract and the strict validator (`parseInboundMessage`) that treats the webview as untrusted input. |
| `src/webview/view.ts` | `ChatViewProvider`: webview lifecycle, restrictive CSP + nonce, `localResourceRoots` limited to `media/`, dispatch of validated messages, and `state`/`delta` posting. |
| `src/providers/adapter.ts` | The future planning-assistant boundary described above. |
| `src/extension.ts` | Activation: settings, directory resolution, wiring, the five commands, and the one-shot auto-connect when the chat is first opened. |
| `media/webview/*` | The chat UI. Plain JS/CSS, no framework, theme tokens only. |

## One turn, end to end

1. `send` from the webview is validated, then `BridgeController.send` runs. If a turn is
   already streaming it is refused here - OpenCode accepts concurrent prompts
   (delivery `steer`), so the gate has to live in Bridge.
2. The controller reuses the active session, or creates exactly one (`ensureSession`).
   A session is created per new chat, never per message.
3. `session.prompt` returns as soon as OpenCode has accepted the message. The local
   "pending" bubble adopts the real inbox message id.
4. Assistant text arrives on the event stream as `session.text.delta`. The first chunk
   for a new message is sent as full `state`; later chunks use the lighter `delta`
   message. Tool activity arrives as `session.tool.*` events.
5. The turn ends on `session.execution.succeeded` / `.failed` / `.interrupted`
   (`session.idle` does not fire for normal turns in 2.0.30). The controller then
   reloads stored messages, which are the source of truth: they fix the final text,
   the real outcome, the tools and the model that was actually used.
6. Session titles are generated by OpenCode, so the session list is refreshed after
   the turn.

If the event stream drops, the controller clears `busy` (so the UI can never wedge),
tells the user it is reconnecting, and resynchronises history when the stream resumes.

## State model

`UiState` is complete and self-describing: connection, workspace, sessions, active
session, model, messages, busy flag, status line, optional setup panel (not connected
or no workspace folder) and optional transient error. `setup` is computed in one place
so the webview stays dumb: it renders what it is told.

## Security model

- **Loopback by default.** `bridge.serverUrl` is rejected unless it is a loopback
  address, unless `bridge.allowRemoteServer` is explicitly enabled.
- **No assumed auth.** Bridge always sends HTTP Basic credentials: the configured
  `bridge.password`, or the password OpenCode writes to its state file. A loopback
  server is not treated as anonymous.
- **The webview never sees credentials.** They exist only in the extension host, in
  the `Authorization` header of the SDK client.
- **The webview is untrusted.** Messages are validated against a fixed type list with
  size limits; anything else is rejected and logged. CSP is `default-src 'none'` with a
  per-load script nonce, and resources are limited to this extension's `media/` folder.
- **Errors are scrubbed.** Known secrets and `Basic`/`Bearer` tokens are stripped from
  every message before it can be displayed, because OpenCode errors can echo request
  URLs.
- **Minimal surface.** No telemetry, no other network calls, and the only thing Bridge
  writes is nothing - it is read-only towards your OpenCode configuration.

## SDK choice

Bridge uses `@opencode/client@2.0.30`, the official client for OpenCode 2.x, matching
the installed CLI version. Note the deviation from the commonly cited
`@opencode-ai/sdk` package: that one speaks the v1 API (routes at the server root),
while OpenCode 2.x serves `/api/*` with Basic auth - the v1 package cannot talk to it.

## Implemented

- Discovery of the local OpenCode service (state file) and manual `bridge.serverUrl`.
- Connection state machine with actionable failure explanations and no false "connected".
- Session list, select, create; never one session per message.
- Streaming assistant text, tool call status, model display.
- Cancellation (`bridge.stopGeneration` and the Stop button) via `session.interrupt`.
- Duplicate-submission gate; failed-send marker with an explicit Retry.
- Authoritative resync from stored messages after every turn and after stream recovery.
- Settings, output-channel logging, five commands, activity-bar chat view.
- 71 hermetic unit tests, a bundle check, and a real end-to-end script
  (`scripts/e2e.mjs`) run against a live OpenCode 2.0.30 server.

## Not implemented (deliberately)

- Any planning assistant, and any ChatGPT/Claude-style auth. The adapter only defines
  the seam; the active assistant is "You".
- A model picker. OpenCode owns model selection; Bridge displays what OpenCode uses.
- Approval/permission UI. Bridge currently shows tool activity but has no approve/deny
  control, and nothing auto-approves on your behalf.
- Message editing, attachments/images, diff viewing, multiple workspaces per window,
  session deletion, and history pagination beyond the newest 50 sessions.
- Publishing: no VSIX is published to the Marketplace.

## Known limitations

- Bridge targets OpenCode 2.x. Against another major version it still connects but
  warns, because the `/api/*` contract may differ.
- Sessions are scoped to a single directory (first workspace folder or
  `bridge.directory`); multi-root workspaces use the first folder only.
- One connection per VS Code window; settings changes require a reconnect.
- The password in `bridge.password` is stored in plain text by VS Code settings; leaving
  it empty and reading OpenCode's state file avoids that.
- Turn detection relies on OpenCode's `session.execution.*` events. If a server version
  stops emitting them, the UI stays busy until the stream recovery path clears it.
